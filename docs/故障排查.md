# 故障排查

> 🟡 固件相关条目尚未在实机验证 —— 实机复现后再补充。

## mock 设备连不上（HTTP 403）

**症状**：连接被拒，日志里出现 `HTTP 403`。

**原因**：环境里全局设了 `HTTP_PROXY` / `HTTPS_PROXY`，而 `websockets` 库默认 `proxy=True` —— 连 `127.0.0.1` 的请求也会被塞进代理，代理不认识本机地址。mock 设备脚本已内置 `proxy=None`，正常不会遇到。

**其他可能**：petd 没起、端口不对。查 `ss -ltn | grep 18860`。

## gateway 连接失败（HTTP 403）

**症状**：

```
WARNING petd.gateway gateway 连接失败(proxy rejected connection: HTTP 403)，1s 后重试
```

**原因**：环境里全局设了 `HTTP_PROXY` / `HTTPS_PROXY`（CI、容器、公司网络常见），
而 `websockets` 库默认 `proxy=True` —— **连 `127.0.0.1` 的请求也会被塞进代理**，
代理不认识本机地址，直接返 403。

**解法**：petd 默认 `gateway.useProxy=false`，走直连。真要连远程 gateway 时，
在 `petd/data/config.json` 里设 `"useProxy": true`。

> 📌 `petd/data/config.json` 不进仓库 —— 它是每台机器自己的配置。
> 首次启动 petd 会自动生成一份，改完 `systemctl --user restart petd` 生效。

> ⚠️ 这条坑在 petd 的 gateway 客户端和 mock 设备脚本上都出现过。
> 任何连本机端口的 WS/HTTP 客户端都要显式 `proxy=None`。

## 连不上 petd

**症状**：设备反复重连，或 mDNS 解析失败。

1. **确认 petd 在跑**：`curl -s http://127.0.0.1:18860/admin/api/session`（这个接口是公开的，不用口令）
2. **确认 mDNS**：`getent hosts petd.local` —— 解析不出就是广播器没起
   - petd 自己就广播 `petd.local`（不走 avahi），先跑 `python3 petd/tools/check_mdns.py` 看广播器活不活
   - 后台 `/admin/api/setup` 的 `mdns.addresses` 为空 = 广播器没起来（看 petd 日志里 mDNS 那行）
3. **设备必须和 petd 在同一个网段** —— mDNS 是组播广播，不跨路由器、不跨 VLAN。设备连 2.4G Wi-Fi、电脑接网线，通常不在一个网段；先把两者都连到同一个 Wi-Fi 热点试
4. **一台机器有两张网卡**（eth0 / wlan0）—— 确认设备在 petd 所在的那个网段，petd 应该在两张网卡上都应答
5. 看设备端 RSSI：太弱（<-70dBm）先挪近点

> **别把 avahi 关掉**：petd 的广播器和 avahi 共用 5353，靠 `SO_REUSEPORT` 共存，
> 两个都活着、互不抢包。实测 avahi 的应答不受影响。

## 黑屏 / 不亮

1. **先看背光**：BL 接 3.3V。如果背光亮但没画面 → 是显示问题；如果背光都不亮 → 供电或接线
2. **背光亮但白屏**：多半是 SPI 接线错（CS/DC/RST），或 `RST` 没接
3. **花屏/撕裂**：检查 SPI 时钟是不是太高、杜邦线太长。换短线试

## 画面显示但内容乱码/花

1. **确认 JPEG 是 4:2:0**：服务端必须 `subsampling=2`，4:2:2/4:4:4 的 MCU 尺寸不同，line buffer 会错位
2. **确认 line buffer 是 16 行**：240×16×2 = 7.68KB
3. **确认宽高**：240(H)×320(V)。屏装反了就上下颠倒

## 画面是倒的 / 转 90°

ST7789 的 `MADCTL` 决定扫描方向。查固件里的 `display.c` 初始化序列，调 `MADCTL` 的位。

## 宠物状态在 idle/working 之间抽搐

**症状**：状态反复闪。

1. 确认稳态窗生效：`data/state_rules.json` 的 `stability.idleAfterMs` 应为 3000
2. 确认事件去抖：`stability.eventDebounceMs` 应为 200
3. 检查是不是后台任务在反复拉起 —— `isBackground=true` 的会话应当被 `exclude` 掉
4. 如果状态卡在 `working` 不退：`hasActiveRun` 可能一直为 true，看 `sessions.list` 原始数据

## 宠物状态不动

1. **petd 是否订阅到 gateway**：看 petd 日志有没有 `sessions.subscribe` 成功
2. **scope 是否被拒**：`FORBIDDEN missing scope: operator.read` → 检查 connect 的 `client.id`/`client.mode` 配对（见 [状态语义](状态语义.md) 与 gateway 接入章节）
3. **是不是全是后台会话**：`isBackground=true` 的会话不参与状态 —— 全是后台时宠物当然是 idle

## gateway 连不上 / scope 被拒

⚠️ **已知的坑**：`client.id` 和 `client.mode` 必须成对，且要与认证方式匹配。

| `client.id` | `client.mode` | 结果 |
|---|---|---|
| `gateway-client` | `backend` | ✅ petd 用这个 |
| `cli` | `cli` | ✅ |
| `cli` | `backend` | ❌ scope 被清空 → `missing scope: operator.read` |
| `petd`（自造） | 任意 | ❌ `INVALID_REQUEST` —— id 是白名单 |

原因：token 认证 + 无设备身份时，源码会清空自荐的 scopes。配对正确就没这问题。

## 设备反复重启

1. **电源纹波**：廉价充电头纹波大，Wi-Fi 电流尖峰可能拉出欠压。必要时并 100µF 电解
2. **OOM**：如果加了全屏帧缓冲就会 OOM → 回到 TJpgDec 流式直刷
3. **看堆内存**：设备定期上报 `{"t":"status","heap":...}`，看最小值

## 旋钮不灵

**先分清是设备没报，还是服务端没收到** —— 设备串口日志里能看到 `knob: event: ...`：

```
knob: event: rot dir=-1 steps=1 ms=0
```

看到这几行 = 硬件、消抖、方向全对，问题在服务端那一侧。
没看到 = 固件侧的事，往下看第 1~4 条。

### 设备侧

1. **不转**：GPIO6 没脉冲 —— 检查接线；KY-040 的 VCC 必须是 3.3V
2. **方向反**：GPIO5 (DT) 读反了，取反即可
3. **一次转报多步**：去抖不够 → 提高最小间隔（≥5ms）
4. **短按长按分不清**：调 `gestures.json` 的 `longPressMs`（服务端，不用刷固件）

### 服务端侧（设备报了事件，屏上却没反应）

**症状**：屏上偶尔会更新，但旋钮按了没反应；petd 日志里出现
`设备连接异常` 或 `设备断开`。

**原因**：服务端处理设备消息时抛异常，WS 处理循环的 `except Exception`
把整条连接掐掉 —— 设备 5 秒后重连、再收一帧、再被掐断。旋钮事件刚发出去
连接就断了，全丢。

**怎么查**：先看 petd 日志有没有 `设备连接异常`；再看设备串口是不是
`ws: disconnected` 反复刷。

**最快复现**：拿 mock 设备对着本机 petd 跑一遍完整链路 ——

```bash
python3 -m petd --host 127.0.0.1 --port 18861 --no-gateway &
python3 -m petd.tools.mock_device --host 127.0.0.1 --port 18861 --rotate --press
```

服务端异常会直接打在 petd 的日志里，不用等真板子。

**确认连接没被掐断**：后台 `/admin/api/status` 的 `device.frames` 是**当前这次连接**
推了多少帧，断线重连会归零重数。连接正常时它持续涨；如果每次重连都只涨个位数，
说明连接还是被掐断了。

`petd/data/setup_state.json` 的 `maxFrames` 是**历史高水位**（在连接/断开时各记一次），
不是实时计数。它停在一个很小的数上（比如 2）说明历史上每次重连只推了一帧就断；
修好之后这个数会跳到几千。

## 字体/文字显示成方块

设备端**不该**有中文字库。如果发现设备在渲染文字，说明走错了路径 —— 文字应该由 petd 用 Pillow 渲染进 JPEG。

## 换了屏之后颜色不对

ST7789 换面板（TN ↔ IPS）**控制器不用换**，驱动照用。但有三个编译期参数可能要调，
都在 `firmware/main/display.c`：

| 现象 | 改哪个 |
|---|---|
| 颜色发白发灰、像负片 | `LCD_INVERT_COLOR` 翻 `true` / `false`（默认 `false` = 0x20 INVOFF，按模组厂商示例） |
| 红蓝互换 | 先翻 `LCD_RGB_ORDER` 改 `LCD_RGB_ELEMENT_ORDER_BGR`；还不对再翻 `LCD_DATA_ENDIAN` 改 `LCD_RGB_DATA_ENDIAN_LITTLE` |
| 画面转 90 度 | `display.h` 的 `DISP_SWAP_XY` 改 1，并把 `DISP_WIDTH` / `DISP_HEIGHT` 对调 |
| 上下颠倒 | 屏装反了，或调 `MADCTL` 的位 |

**这些都编译进固件** —— 改完要重新编译并 USB 重刷（本项目不做 OTA）。

### 首屏自检色条

设备**进配网模式时**先亮 5 秒色条（首次开机，或按住旋钮 5 秒重进配网）：

```text
┌──────────────────────┐  ← 黑色区，左上角一个白色 L 形角标
│ ▓                    │
│ ▓                    │
├──────────────────────┤
│ 红色带               │  ← 字节序/BGR 配错这里就变蓝
├──────────────────────┤
│ 绿色带               │
├──────────────────────┤
│ 蓝色带               │
├──────────────────────┤
│ 白色带               │  ← 反相配错这里会全黑
└──────────────────────┘
```

对着色条逐项看：

| 现象 | 原因 | 改哪个 |
|---|---|---|
| 红色带显示成蓝、蓝色带显示成红 | 字节序或 BGR 配错 | `LCD_RGB_ORDER` / `LCD_DATA_ENDIAN` |
| 白色带显示成黑色（其余正常） | 颜色反相配错 | `LCD_INVERT_COLOR` 翻 `true` |
| 整屏颜色发白发灰、像负片 | 颜色反相配错 | `LCD_INVERT_COLOR` 翻 `true` |
| 白色 L 形角标不在左上角 | 画面方向错了 | `DISP_SWAP_XY` 改 1 并对调宽高 |
| 角标在但整幅画上下颠倒 | 屏装反了 | 调 `MADCTL` 的 MY 位 |

细节见 [固件构建](固件构建.md) 的字节序那节。

**日常开机不显示色条** —— 只有进配网模式才亮。配好网之后想再看，
按住旋钮 5 秒重进配网模式即可。
