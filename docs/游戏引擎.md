# 游戏引擎（设备端小游戏）

> 已实现：引擎代码在 `firmware/main/game/`，游戏包在 `petd/packs/`（骰子、贪吃蛇、消砖块、打地鼠、钓鱼）。
> 文中数字分两类：**实测**（来自现有代码与实机）、**估算**（设计推算，实现时要重新核）。

## 目标

设备自带一组小游戏，**断网也能玩**。

游戏跑在设备固件里，不依赖 petd、不依赖 OpenClaw、不依赖 LLM、不依赖互联网。
petd 在，只负责把游戏包推给设备；petd 不在，设备照玩。

## 为什么游戏必须在设备上，不在服务端

服务端渲染是「整帧 JPEG → 设备解码 → SPI 推全屏」（实测见 `docs/固件构建.md`）：

| 路径 | 每帧字节 | 26MHz SPI 耗时 | 帧率 |
|---|---|---|---|
| 整帧 JPEG（240×320×2） | 153,600 | ≈47ms（+解码 2ms） | **≈20fps** |
| 局部刷新（挡板+球+一格砖 ≈1.1KB） | ~1,100 | ≈0.3ms | 60fps 无压力 |

服务端推帧的活动帧率是 10fps（`petd/config.py` 的 `frame.activeFps`）。球每帧要动的游戏走这条路，
球会一顿一顿还叠网络往返 —— **消砖块在服务端做不了**。

反过来，**不需要连续动画的玩具可以留在服务端**（现在的骰子就是这样：服务端算好一帧覆盖层推下去）。
但本设计把骰子也搬进设备，让整个游戏体系只有一套。

## 硬约束

这些是设计前提，不是可选项：

| 约束 | 原因 |
|---|---|
| **OTA 只由人点** | 设备永远不自己升级；后台点下才刷（`docs/部署手册.md`） |
| **不做游戏商店 / 账号 / 评分 / 排行榜** | 我们是开发者，不是发行平台。仓库给参考实现，用户自己开发 |
| **不做历史记录** | 小游戏就是小游戏：开始 → 玩 → 结束 → 回菜单，不留痕 |
| **游戏是数据包，不是代码** | 加游戏不能刷固件。加一个游戏 = 加一个 pack 文件 |
| **我们只维护自己那几个** | 消砖块、贪吃蛇、骰子、打地鼠。俄罗斯方块往后放，不做 |
| **不限制用户自创作** | 用户把自己的 pack 放进 `petd/data/packs/` 就能用 —— 无审核、无白名单，见「自创作游戏包：能力边界」 |

**「OTA 只由人点」和「游戏是数据包」是同一个决定的两面** —— 就算能刷固件，也不该靠刷新固件来加游戏，
游戏就必须以数据形式存在。这两条互为因果，不是两个独立需求。

## 交互

| 手势 | 屏幕状态 | 行为 |
|---|---|---|
| 短按 | 宠物 | 打开游戏菜单 |
| 短按 | 菜单 | 确认，开始游戏 |
| 旋转 | 菜单 | 上下选择 |
| 旋转 | 游戏内 | 游戏自己定义（挡板移动 / 转向 / 瞄准…） |
| 短按 | 游戏内 | 游戏自己定义（发球 / 放下 / 确认） |
| 长按 | 任意 | 退出游戏 → 回菜单 |

**短按打开游戏菜单** —— 菜单里是游戏列表（骰子、贪吃蛇、消砖块、打地鼠），菜单本身画在设备上（`firmware/main/game/game_menu.c`）。

**长按退出在设备侧判定。** 设备已经能从 `welcome` 里拿到服务端的 `longPressMs`
（`firmware/main/ws_client.c` 已解析这个字段），所以设备自己分得清短按/长按，
不需要新增协议字段。

## 架构

固件里的游戏部分分三层：

```
┌─────────────────────────────────────────┐
│  Runtime     固定步长 60Hz 循环 · 模式状态机 · 输入分发 │
├─────────────────────────────────────────┤
│  Components  组件库：空间/形状/碰撞/网格/行为/渲染     │
├─────────────────────────────────────────┤
│  Pack loader 读 SPIFFS → 解析 JSON → 校验能力 → 建场景   │
└─────────────────────────────────────────┘
```

**关键约束：引擎里不许出现游戏语义。** 没有 `brick`、没有 `paddle`、没有 `snake` ——
只有 rect / circle / grid / trail / gauge 这类通用组件。
新游戏靠**组合**已有组件，不靠加 if 分支。这是「前期兼容」的根本。

## 能力表（引擎原语）

这张表就是「引擎能承载什么」的答案。**写游戏只能用表里的东西**；
表里没有的，要么改需求，要么给引擎加一个新原语（那是一次固件改动）。

能力表只有一处真相：固件 `firmware/main/game/game_comp.c` 里的 `s_caps[]`。
pack 的 `requires` 里出现表外的名字 → 固件拒绝加载，屏上提示要更新固件。
`tools/lint_packs.py` 读同一个数组来校验仓库里的 pack。

### 已实现

| 能力 | 参数 | 说明 |
|---|---|---|
| `rect` | w, h | 轴对齐矩形 |
| `circle` | r | 圆 |
| `cell` | gx, gy | 网格单格 |
| `trail` | len | 记录最近 N 个位置（贪吃蛇身体） |
| `value` | min, max | 显示一个数，形状自动切成数字方块 |
| `sprite` | 资源名, frames | 位图精灵，来源：pack 自带的 `sprites` |
| `grid` | cols, rows, x, y, cell | 网格坐标系，实体按格走 |
| `heading` | up/right/down/left | 朝向，决定网格步进方向 |
| `vel` | vx, vy, ax, ay | 速度与加速度，每逻辑步积分 |
| `collide` | solid, bounce, restitution | 像素空间的实体碰撞（圆↔圆、圆↔矩形、矩形↔矩形） |
| `bounds` | x0, y0, x1, y1, walls | 撞边界反弹；没设成墙的一侧掉出去触发 `bounds` 事件 |
| `pattern` | pattern, colors | 网格图样：一组实心格 + 每格颜色 |
| `move_cell` | value, value2 | 网格实体按格移动（每步 dx 格、dy 格），越界夹在场地内；网格开了 `wrap` 就首尾相接 |
| `wrap` | — | 网格首尾相接：走过头绕回另一头（打地鼠六格环靠它） |
| `outline` | — | 格子实体画成边框而不是实心（光标用） |
| `overlap` | — | 网格实体与网格实体重叠 |
| `intent_overlap` | — | 意图触发时目标实体碰到了别的实体 |
| `self` | — | 网格实体撞到自己 |
| `oob` | — | 网格步进出界 |
| `timer` | intervalMs, repeat | 周期触发事件 |
| `score` | — | 计分板 |
| `value` | — | 见上 |

**形状**：`rect` / `circle` / `cell` / `trail` / `value` / `sprite`。

**精灵**：pack 在 `sprites` 里自带位图帧（12×16 内的点阵 + 调色板），`scale` 控制放大倍数。
不支持精灵旋转 —— ST7789 没有硬件旋转，软件转 240×320 全屏太贵。

**碰撞响应**：撞到实心体时，`bounce: true` 的一侧由引擎推出重叠区并沿法线反射速度，
`restitution` 是恢复系数（1 = 完全弹性）。检测组合：圆↔圆、圆↔矩形、矩形↔矩形。

**网格图样**：`pattern` 是字符串数组，字符是颜色键（`.` 和空格是空格）；
`colors` 把字符映射到颜色。实心格参与碰撞，可以被 `destroy_cell` 销毁。

### 事件

`start`（开局）、`intent`（输入映射到意图）、`overlap`（网格实体重叠）、
`self`（撞自己）、`oob`（网格出界）、`timer`（定时器）、
`hit`（实体撞实体）、`grid_hit`（实体撞网格实心格）、
`bounds`（掉出边界）、`empty`（网格实心格全清空）、
`intent_overlap`（意图触发时目标实体碰到了东西）。

`intent_overlap` 判在**意图规则执行之前** —— 先看碰到了没有，再改状态。
反过来做，「敲下去」这种一边判定一边改位置的动作会落在改完之后的位置上，
对不上玩家按下去的那一瞬间。

### 效果

`set_pos` / `set_vel` / `add_vel` / `turn` / `reverse` / `show` / `hide` /
`grow` / `add_score` / `randomize` / `destroy` / `win` / `lose` /
`start_timer` / `stop_timer` / `move` / `move_cell` / `advance_cell` / `destroy_cell`。

`move` 按输入方向位移（`value` 是每步 dx，`value2` 是每步 dy）；
`move_cell` 走的是网格坐标（`value` 是每步 dx 格，`value2` 是每步 dy 格），
旋钮转几步就挪几格，越界夹在场地内（网格开了 `wrap` 就首尾相接）；
`advance_cell` 沿 +x 前进 `value` 格，**不看输入方向** —— 定时器事件没有方向，
地鼠「按节奏轮换格位」靠它；
`destroy_cell` 销毁刚被命中的那个格（`grid_hit` 事件记下的坐标）。

`turn` 转 90° 一格：`heading` 是方向序号（0 上 1 右 2 下 3 左），
一次手势最多转 90° —— 快甩旋钮不会把蛇转一整圈。

**没有音效。** 这块板没有蜂鸣器，背光也没 PWM（`firmware/main/display.c` 注释：
「背光 BL 直接接 3.3V，不受控」）—— 反馈全靠画面。

## Pack 格式

一个 JSON 文件就是一个游戏。格式定死，以后加游戏照着填。

```json
{
  "id": "brickout",
  "version": 1,
  "order": 10,
  "title": "消砖块",
  "hint": "旋转移挡板 · 按下发球 · 长按退出",
  "requires": ["rect", "circle", "vel", "collide", "bounds", "pattern", "grid", "score"],

  "grid": {
    "cols": 9, "rows": 5, "x": 12, "y": 30,
    "cell": 24, "cellW": 24, "cellH": 12,
    "border": true, "borderColor": "#5C4033",
    "pattern": ["111111111", "111111111", "111111111", "111111111", "111111111"],
    "colors": { "1": "#C80000" }
  },

  "intents": [
    { "name": "move_x", "target": "paddle" },
    { "name": "fire",   "target": "ball" }
  ],
  "input": {
    "rot":   { "intent": "move_x" },
    "press": { "intent": "fire" }
  },

  "entities": [
    { "id": "paddle", "shape": "rect", "x": 120, "y": 292, "w": 44, "h": 8,
      "color": "#5C4033", "solid": true },
    { "id": "ball", "shape": "circle", "x": 120, "y": 270, "r": 4,
      "vx": 0, "vy": 0, "color": "#E8B000",
      "bounce": true, "restitution": 1.0,
      "bounds": { "x0": 0, "y0": 0, "x1": 240, "y1": 320, "walls": "lrt" } }
  ],

  "rules": [
    { "on": "intent", "intent": "move_x", "target": "paddle",
      "effects": [ { "fx": "move", "target": "paddle", "value": 6, "value2": 0 } ] },
    { "on": "intent", "intent": "fire", "target": "ball",
      "effects": [ { "fx": "set_vel", "target": "ball", "value": 1.6, "value2": -2.0 } ] },
    { "on": "grid_hit", "target": "ball",
      "effects": [ { "fx": "destroy_cell" }, { "fx": "add_score", "value": 10 } ] },
    { "on": "empty", "effects": [ { "fx": "win" } ] },
    { "on": "bounds", "target": "ball", "effects": [ { "fx": "lose" } ] }
  ]
}
```

**速度单位是像素/逻辑步** —— 一个逻辑步是 1/60 秒，`vx: 1.6` 就是每步走 1.6 像素。

**`bounds.walls` 里 l/r/t/b 表示哪几条边是墙** —— 上面这版左右上有墙、下面没有，
球掉出下边界就触发 `bounds` 事件。

**实心格参与碰撞** —— `pattern` 里的字符是实心格（`.` 和空格是空格），
撞到会触发 `grid_hit`，规则里用 `destroy_cell` 消掉它。


### 中文怎么办

pack 自己带字模。`glyphs` 字段把用到的汉字映射成 12×12 位图（base64）。
仓库里放一个生成脚本 `tools/gen_pack_glyphs.py` —— 读 pack、找出所有汉字、
用系统 CJK 字体渲染成 12×12 点阵、写回 pack。
这样**加游戏不需要重刷固件就能显示中文**，也不用多开一条资源下发通道。

## 能力协商

pack 的 `requires` 声明它要用哪些能力。固件缺能力时：

- **解析阶段就拒收** —— 不写 SPIFFS，设备回 `packAck ok=false`，后台日志里能看到
- **菜单里不会出现这个游戏** —— 没装上就没有这一项
- 不许黑屏、不许乱跑

失败是安全的（不装、不崩），但**目前没有屏上提示** ——
老固件上的玩家只会发现菜单里少了一项，不会知道是固件太老。
这一版没有补这句文案；要补得往引擎字表里加字，见「尚未实现」。

pack 的 `version` 与固件支持的 pack 版本比较，不匹配同样走可读失败。

## 协议新增

协议**保持 v1**，全部是向后兼容的增量：

| 方向 | type | 载荷 |
|---|---|---|
| petd → 设备 | `pack`（新） | **文本预告**，紧跟一条 binary 消息（pack 原文） |
| 设备 → petd | `packAck`（新） | `{"type":"packAck","id":"brickout","ok":true}` |

pack 本体走 binary，字节与 pack 文件完全一致 —— 设备原样写进 SPIFFS，
不在设备上重新序列化 JSON（JSON 序列化会走 newlib 的浮点 printf，栈开销大）。

装包在设备上由独立任务执行，不在 WebSocket 回调栈上：回调栈只有 4KB，
装不下解析加写盘。

其余靠**已有消息加字段**，不新增消息类型：

| 消息 | 新增字段 | 用途 |
|---|---|---|
| `hello`（设备 → petd） | `packs` | 设备报告 SPIFFS 里已有哪些包。petd 对比后只补缺的 |
| `status`（设备 → petd） | `mode` | `idle` / `menu` / `playing`。petd 据此停推帧 |

`hello.packs` 让整个下发流程**自愈**：每次重连，设备报自己有什么，petd 补差额。
不需要单独的「我要包」消息。

老固件不认识 `pack` 消息会直接忽略（现有的消息分派只认已知 type），
所以**现有设备不受影响**，宠物照常工作。

petd 另有一道版本闸：固件版本低于 `0.5.1` 的设备，一根 pack 都不下发，
握手时给的是空的启用列表。低于这个版本的固件装包会撑爆 WebSocket 回调栈，
设备会反复重启。

## 固件改动清单

**新增**：上面 `firmware/main/game/` 全部文件；`game_pack.c` 里挂载 SPIFFS。

**修改**：

| 文件 | 改什么 |
|---|---|
| `firmware/main/CMakeLists.txt` | 加 game 源文件；REQUIRES 加 `spiffs` |
| `firmware/main/app_main.c` | screen_task 分成「宠物屏」和「游戏屏」两条路；knob_task 在游戏模式下把事件交给引擎而不是转给服务端 |
| `firmware/main/ws_client.c` | 二进制帧到达时，若设备在游戏模式则**不画**（否则会覆盖游戏画面）；收 pack 本体 + 装包任务 |
| `firmware/main/display.c` | 加一个内部 SRAM 的 DMA scratch（**SPI DMA 源不能是 PSRAM**） |

**完全不动**：显示驱动核心、旋钮驱动（它只报原始量，正好）、WS 框架、配网、宠物渲染管线。

**空间核算**（实测）：

| 项 | 数字 |
|---|---|
| `fw-v0.5.2` petd.bin | 1023 KB |
| `fw-v0.5.2` merged-binary.bin | 1151 KB |
| app 分区（factory/ota_0/ota_1） | 各 2 MB → **约 1 MB 余量** |
| `storage` 分区 | **1 MB SPIFFS，已划好，固件从未挂载过** |
| 全屏画布（PSRAM 240×320×2） | 150 KB（PSRAM 8MB，够） |
| DMA scratch（内部 SRAM） | 几 KB |

**内存注意**：画布可以放 PSRAM，但**每次推给屏的源缓冲必须在内部 SRAM**
（SPI DMA 不能从 PSRAM 取源）。球 8×8、挡板 44×8 分别只要 128 / 704 字节。

## 中文点阵

设备内置 5×7 ASCII（`firmware/main/ascii_font.h`）。中文用 12×12 位图，
由 pack 自带、仓库脚本生成。

**12×12 的取舍**：比 16×16 小一圈，一行能放 20 个字（240px）。生成脚本 `tools/gen_pack_glyphs.py` 用 PIL 渲染 12px 中文字体，
像素灰度 ≥96 记为一点（`GLYPH_W = GLYPH_H = 12`，阈值 96）。

| 能力表不漂移 | 校验脚本直接读 `game_comp.c` 里的 `s_caps[]` —— pack 声明表外的能力就红 |

| 引擎行为 | `tests/fw_host/run.sh`：在开发机上编译固件的物理与事件逻辑，跑反弹、消格、边界、胜负的行为断言 |

「前期兼容」的护栏是能力表只有一处真相：固件的 `s_caps[]` 是唯一来源，
校验脚本和 pack 都以它为准，改一边另一边没改，CI 就红。

## 自创作游戏包：能力边界

引擎与游戏本体**不做绑定**：游戏是一份 JSON 数据包，引擎只认包里声明过的能力、事件、效果。
这一章写给**自己写游戏包的人** —— 动手前对着它过一遍：能做的直接做，做不到的就地知道该改设计还是该改引擎。

下面每条都有代码依据。**限制说的是「现在还没做到」，不是「不许做到」**：想突破任何一条，见本章最后一节。

### 装进去：用户目录优先，没有准入闸

```
petd/packs/        仓库自带（消砖块 / 贪吃蛇 / 骰子 / 打地鼠 / 钓鱼）
petd/data/packs/   用户自己放的
```

`petd/packs.py` 的 `_roots()` 先扫用户目录再扫内置目录，**同名盖掉内置的**。
没有白名单、没有审核、没有签名 —— 放进去就能用。

用户目录已在 `.gitignore` 里（跟皮肤 / 相册 / 背景一样），自己的包不会被 `git add .` 带进仓库。

设备侧仍有能力协商：pack 的 `requires` 里出现固件不认识的能力名，解析阶段就拒收
（不写 SPIFFS、菜单里不出现这一项、宠物照常工作）。这是**能力不足的失败**，不是**内容准入的拒绝**。

所以「我们只维护自己那几个」是维护承诺，不是准入限制。仓库里那四个只是参考实现。

### 引擎能力清单

| 类别 | 数量 | 内容 |
|---|---|---|
| 能力 caps | 21 | rect / circle / cell / trail / value / sprite / grid / heading / vel / collide / bounds / pattern / move_cell / wrap / outline / overlap / intent_overlap / self / oob / timer / score |
| 效果 fx | 21 | set_pos / set_vel / add_vel / turn / reverse / show / hide / grow / add_score / randomize / destroy / win / lose / start_timer / stop_timer / move / move_cell / advance_cell / destroy_cell / set_frame（外加 none 空效果） |
| 事件 | 11 | start / intent / overlap / self / oob / timer / hit / grid_hit / bounds / empty / intent_overlap |
| 形状 | 6 | rect / circle / cell / trail / value / sprite |

`caps` 声明「这个游戏要用哪些能力」，固件按 `s_caps[]` 校验；
`fx` 是规则里能执行的动作，事件是能触发的时机。各能力参数见上文「能力表（引擎原语）」。

### 上限与配额

| 项 | 上限 | 常量 |
|---|---|---|
| 实体 | 12 | GAME_MAX_ENTITIES |
| 规则 | 24 | GAME_MAX_RULES |
| 意图 | 8 | GAME_MAX_INTENTS |
| 定时器 | 2 | GAME_MAX_TIMERS |
| 能力声明 | 24 | GAME_MAX_CAPS |
| 字形 | 256 | GAME_MAX_GLYPHS |
| 精灵 | 4 | GAME_MAX_SPRITES |
| 精灵帧 | 8 | GAME_MAX_SPRITE_FRAMES |
| 精灵尺寸 | 16×16 | GAME_MAX_SPRITE_W / H |
| 精灵调色板 | 4 色 | GAME_MAX_SPRITE_PAL |
| 启用包数 | 32 | GAME_MAX_ENABLED |

精灵这套预算够做一个有角色动画的游戏：4 个精灵 × 8 帧 × 16×16 × 4 色调色板，
还有 `scale` 放大和 `frame_from_value`（数值决定帧号）。现在只被骰子用了四分之一。

### 三条结构性约束

这三条不是「缺个原语」，靠声明绕不过去。

**1. 实体必须预置，运行期不能生成。**
`nents` 只在解析包时增长，引擎里没有任何 spawn 路径。
**12 个实体是硬预算** —— 子弹、刷怪、发射物这一类全部做不到。
替代做法：预置好所有可能出现的实体，用 `show` / `hide` 切换。

**2. 规则是「首个命中的固定反应」，没有条件表达式。**
`match_rule` 按顺序扫 `rules[]`，只比事件类型 + `intent` / `timer` / `target` / `other`，
命中就返回 —— **第一个命中的规则赢，后面的不再看**。
所以规则的书写顺序就是优先级；问不了「分数 > 10 时换行为」。
`other` 和 `target` 能补一点条件，但仍然没有数值比较。

**3. 网格与像素是两套坐标系，互不碰撞。**
`cell` 实体只跟 `cell` 实体比格子，`rect` / `circle` 只跟像素实体比。
一个包里可以混用两套，但**格子墙撞不到像素球**。

### 现在能做什么，做不了什么

**能（不改引擎）**

| 类型 | 例子 | 配方 |
|---|---|---|
| 网格 | 接落物、挖墙迷宫、绕圈追逐（钓鱼） | grid + pattern + cell + move_cell / advance_cell / destroy_cell |
| 像素 | 躲避、俯视赛车、弹跳 | circle / rect + vel + collide + bounds |
| 轨迹 | 贪吃蛇类变体 | trail + heading + self + oob |
| 决策 | 反应速度、老虎机 | timer + value + randomize + sprite |
| 时机 | 钓鱼、节拍 | timer + intent_overlap + 双定时器切阶段 |

**旋钮步数是可用的**：`move_cell` 按有符号步数移动，旋钮转几步就挪几格
（越界夹在场地内，网格开 `wrap` 则首尾相接）。
`turn` 才是转向，一次手势最多 90°（`heading` 是 0 上 1 右 2 下 3 左）。

**做不了（结构性）**

- **需要状态判断的玩法（最根本的一条）** —— 引擎没有状态机，也没有条件表达式。
  `match_rule` 只比「事件类型 + intent + timer + target + other」，命中第一条就 return；
  没有 else、没有 fallthrough、没有数值比较、没有布尔标志位。
  状态载体也读不了：`value` 只能被 `randomize` 改（随机数），没有「设为 X」的效果；
  `visible` 能当布尔位但规则匹配读不到它；`score` 可读可写但没有规则去读它。
  所以游戏只能是**「事件 → 固定反应」的直线流程** ——
  **扫雷、翻牌记忆、猜大猜小都做不了**（都要比较数值），
  「连错三次就输」「血条见底就结束」也做不了。
- 运行期生成实体的玩法（弹幕、刷怪、发射子弹）
- 需要条件判断的玩法（血条、过关变难、分数阈值换行为）
- 斜向 / 任意角度（`heading` 只有 4 个方向序号）
- 网格 × 像素混合碰撞
- 俄罗斯方块 / 2048 这类需要数组语义的玩法（实体不能当数组用，12 个也放不下 16 格）
- 游戏内长按做别的事（长按固定是退出游戏）

**绕过状态判断的两个手法**：

1. **事件互斥代替条件** —— 玩家先按 → `win`，定时器先到 → `lose`。
   「谁先发生」本身就是判断。
2. **多定时器切阶段** —— `start_timer` / `stop_timer` 可以让不同的规则只在不同阶段生效。
   钓鱼就靠这个做「第一条鱼 → 第二条鱼（更快）→ 胜利」。

其它已知缺口见「尚未实现」（`gauge` / `progress` / 线段 / 精灵旋转等）。

### 想要更多：扩展引擎

按代价从低到高：

| 缺口 | 改哪儿 | 代价 |
|---|---|---|
| 网格 × 像素统一碰撞 | `game_find_overlap` 的类型过滤 | 低 —— 一次性实现，长期最划算 |
| 运行期生成实体 | 实体池加回收位，`destroy` 时归还 | 中 —— 动内存结构和 12 的上限 |
| 条件判断 | `match_rule` 加数值比较 | 高 —— 会破坏「规则是纯事件匹配」这条简洁性 |

改引擎的规矩不变：**引擎里不许出现游戏语义**（没有 `brick`、没有 `paddle`）。
新原语必须是通用平台能力，不是某个游戏的专用后门；
一个游戏要加三个以上专属原语，说明设计该重做了。

**动手前先掂量要不要做。** 四个游戏对一只桌面宠物已经不少，
第五个游戏的边际收益远低于把现有四个做顺手。

## 边界

- OTA 只由人点，设备不自己升级
- 不做平台（商店 / 账号 / 排行 / 审核）
- 不做历史记录
- 短按 = 游戏菜单，长按 = 退出
- 骰子搬进设备
- 中文菜单标题
- 退出后不做宠物反应
- 游戏是数据包，加游戏不刷固件
- 不限制用户自创作游戏包（用户目录优先，无审核无白名单）
- 俄罗斯方块往后放，不做

实现上的既定选择：

- `gauge`（value + target + tolerance）固件里还没有 —— 想做力度条/张力表这类玩法时再补
- 中文点阵 12×12，字号与阈值见「中文点阵」一节
- 局部刷新走 SPI 直刷，不做整屏重绘；LCD 无残影
- 菜单由引擎画（`firmware/main/game/game_menu.c`），不复用服务端那套卡片渲染
