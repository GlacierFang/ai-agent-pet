## ⚠️ N8R8 的 PSRAM 配置

N8R8 = **8MB Octal PSRAM**。ESP-IDF 里八线 PSRAM 需要专门的 sdkconfig 选项，**配错的后果是固件静默地找不到 PSRAM** —— 编译能过，跑起来行为像没有 PSRAM。

**根因**：ESP-IDF 的 `choice SPIRAM_MODE` **默认是 `SPIRAM_MODE_QUAD`**。芯片是 Octal 时，quad 实现跑不起来，PSRAM 初始化被放弃，`esp_psram_get_size()` 返回 0。

### sdkconfig.defaults（🟢 选项名已一手核对 ESP-IDF 源码）

```ini
# ── PSRAM：八线 Octal ─────────────────────────────
CONFIG_SPIRAM=y
CONFIG_SPIRAM_MODE_OCT=y          # ⭐ 最关键：默认是 QUAD，配错就找不到 PSRAM
CONFIG_SPIRAM_TYPE_AUTO=y
CONFIG_SPIRAM_SPEED_80M=y          # 默认是 40M；120M 对 Octal 是实验特性，不碰

# ── 内存分配策略 ─────────────────────────────────
CONFIG_SPIRAM_BOOT_INIT=y
CONFIG_SPIRAM_USE_MALLOC=y
CONFIG_SPIRAM_MALLOC_ALWAYSINTERNAL=4096    # 默认 16384；调小 = 更多大块走 PSRAM
CONFIG_SPIRAM_MALLOC_RESERVE_INTERNAL=32768  # 默认值

# ── Flash：N8 = 8MB Quad ────────────────────────
CONFIG_ESPTOOLPY_FLASHSIZE_8MB=y
CONFIG_ESPTOOLPY_FLASHSIZE="8MB"
CONFIG_ESPTOOLPY_FLASHMODE_DIO=y   # 见下方「Flash mode」说明
```

**已核实的默认值**（ESP-IDF `components/esp_psram/Kconfig.spiram.common`）：

| 选项 | 默认 | 我们设成 | 备注 |
|---|---|---|---|
| `SPIRAM_MODE_QUAD` / `_OCT` | **QUAD** | OCT | ⭐ 不改就找不到 PSRAM |
| `SPIRAM_TYPE_AUTO` | AUTO | AUTO | |
| `SPIRAM_SPEED_40M` | **40M** | 80M | 120M 对 Octal 是实验特性（温度漂移会随机崩），**不用** |
| `SPIRAM_BOOT_INIT` | y | y | |
| `SPIRAM_USE_MALLOC` | — | y | |
| `SPIRAM_MALLOC_ALWAYSINTERNAL` | 16384 | 4096 | 调小让大块分配走 PSRAM |
| `SPIRAM_MALLOC_RESERVE_INTERNAL` | 32768 | 32768 | |

## 配网

设备自带 **SoftAP 配网页面**（`firmware/main/provision.c`）。

首次上电没有 Wi-Fi 凭据 → 设备起一个热点 `petd-setup-XXXX`，屏幕上显示热点名和 8 位密码。手机连上那个热点，浏览器打开 `http://192.168.4.1`，填 Wi-Fi 名称密码 → 设备写进 NVS 并重启。

**不需要编译，也不需要改代码。** 凭据存在设备 NVS 里，断电不丢。

编译期宏 `PETD_WIFI_SSID` / `PETD_WIFI_PASS` 是给「NVS 还没有但想直接连上」的开发者兜底用的 —— CI 不注入这两个值。

## mDNS 发现

设备用 mDNS 找 petd（`petd.local`），避免写死 Pi 的 DHCP 地址（Pi 有 eth0 / wlan0 两个网段，IP 会变）。

- lwIP 侧开启 `CONFIG_LWIP_DNS_SUPPORT_MDNS_QUERIES`（`sdkconfig.defaults`）—— 让 lwIP 的 DNS 解析器能解析 `.local` 域名
- 服务端在 UDP 5353 上应答（`petd/mdns.py`，纯标准库实现，不装 zeroconf）
- 配网页面里也能直接填服务端地址，留空就用 `petd.local`

## 显示管线

```
JPEG 字节流 → TJpgDec → 16×16 MCU → 逐块 SPI DMA → ST7789
```

**不用全屏帧缓冲。** 240×320×2 = 150KB 单块 malloc，在 Wi-Fi 栈起来后内部 SRAM 碎片化严重，有 OOM 风险。

用 TJpgDec 的 MCU 流式直刷：line buffer 只要 240×16×2 = **7.68KB**，解出一块推一块。

**配套约束**：服务端渲染固定 `quality=85, subsampling=2`（4:2:0），保证 JPEG 的 MCU 是 16×16，line buffer 正好一块。4:2:2 / 4:4:4 的 MCU 尺寸不同，line buffer 规格要跟着改。

## 实现细节：TJpgDec → esp_lcd 的衔接

> 🟢 以下基于 ESP-IDF v5.5 源码一手核对（`components/esp_lcd/spi/esp_lcd_panel_io_spi.c`、`src/esp_lcd_panel_ops.c`）。

### ⚠️ 关键约束：`draw_bitmap` 是异步的 → 单缓冲会撕裂

`esp_lcd_panel_draw_bitmap()` → `panel->draw_bitmap()` → `panel_io_spi_tx_color()`，后者：

- 用 `spi_device_queue_trans()` **排队**发送（不是阻塞发送）
- 事务池 `trans_pool` 有 `queue_size`（= `trans_queue_depth`）个槽位
- 只有池满时才 `spi_device_get_trans_result()` 阻塞回收

**含义：函数返回时，DMA 可能还在读你传进去的 buffer。**

所以如果在 TJpgDec 输出回调里直接 `draw_bitmap(s_line_buf)` 然后继续解码下一块，**上一块的 DMA 还没读完就被覆盖** → 花屏/撕裂。这是本项目最容易踩的实现坑。

| 方案 | 说明 |
|---|---|
| **A. 双缓冲（推荐）** | 两份 7.68KB line buffer 交替；推完 A 等 DMA 完成再推 B。解码与传输可重叠，总耗时取二者较大值而非相加 |
| B. 同步等待 | 每次 `draw_bitmap` 后等传输完成再解码下一块。简单但丢掉流水线重叠 |

### TJpgDec 侧的要求

#### ⚠️ 先选对源码版本 —— 这决定了你能开哪些开关

🟢 **上游 ChaN R0.03（2021）已经和 RT-Thread 那个 fork 不是同一份代码了。**

| | RT-Thread fork | **上游 R0.03（推荐）** |
|---|---|---|
| 版本 | 2012 R0.01b | **2021 R0.03** |
| 配置文件 | 宏直接写在 `tjpgd.h` | **独立 `tjpgdcnf.h`** |
| `JD_FORMAT` | 被 `TJPGD_USING_FORMAT_RGB565` 包着 | **`tjpgdcnf.h` 里直接写死 `1`** |
| `JD_FASTDECODE` | ❌ **不存在** | ✅ **存在，三档** |
| `JD_ACCURATE` | ❌ 不存在 | ❌ 不存在 |
| `JD_SZBUF` | `TJPGD_INPUT_BUFFER_SIZE`（要自己定义） | **`512`**（默认值，要调） |
| `JD_TBLCLIP` | ✅ 有 | ✅ 有 |
| `JD_USE_SCALE` | ✅ 有 | ✅ 有 |

**结论：用上游 R0.03，别用 RT-Thread 那个 2012 年的 fork。** 理由：`JD_FASTDECODE` 在上游是三档可调的解码优化，在那个 fork 里根本不存在（写它不会报错，只会让你以为开了加速）。

#### 上游 R0.03 的 `tjpgdcnf.h` 全文（照抄改即可）

```c
#define JD_SZBUF        512
/* Specifies size of stream input buffer */

#define JD_FORMAT       1
/* Specifies output pixel format.
   0: RGB888 (24-bit/pix)
   1: RGB565 (16-bit/pix)   ← 我们要这个
   2: Grayscale (8-bit/pix)
*/

#define JD_USE_SCALE    1
/* Switches output descaling feature. 0: Disable 1: Enable */

#define JD_TBLCLIP      1
/* Use table conversion for saturation arithmetic. A bit faster, but +1 KB code size. */

#define JD_FASTDECODE   1
/* Optimization level
   0: Basic optimization. Suitable for 8/16-bit MCUs.
   1: + 32-bit barrel shifter. Suitable for 32-bit MCUs.   ← S3 是 32 位，选这个
   2: + Table conversion for huffman decoding (wants 6 << HUFF_BIT bytes of RAM)
*/
```

**⚠️ `JD_FORMAT` 有第三种值 2 = 灰度 8bpp** —— RT-Thread fork 的注释里没提，上游有。我们用 1。

**⚠️ `JD_SZBUF` 默认只有 512 字节** —— 太小。JPEG 是变长码流，512 字节的输入缓冲会导致解码器频繁回调取数，拖慢速度。**建议改到 2048 或 4096**（内部 SRAM 够）。

**`JD_FASTDECODE` 选 1** —— S3 是 32 位 MCU，能用 32 位桶移位加速。选 2 还要额外吃 `6 << HUFF_BIT` 字节 RAM 做哈夫曼查表，收益递减。

#### 工作内存

**约 3100 字节**（`JDEC` 结构 + 内存池），必须**连续**内存 —— 复杂哈夫曼表溢出即崩溃。用 `heap_caps_malloc(3100, MALLOC_CAP_INTERNAL)`。

**S3 没有 ROM 版 TJpgDec** → 源码引入是唯一选择（ROM 版只有原始 ESP32 才有）。

一次 `jd_decomp` 需要完整 JPEG 字节流在内存里（8–23KB，PSRAM 够）。

#### ✅ `JRECT` 是像素坐标，不是 MCU 坐标（🔴 已解）

🟢 **上游 R0.03 源码实锤**：

```c
mx = jd->msx * 8; my = jd->msy * 8;      /* MCU size (pixel) */
rx = (x + mx <= jd->width) ? mx : jd->width - x;
ry = (y + my <= jd->height) ? my : jd->height - y;
rect.left  = x;        rect.right = x + rx - 1;   /* Rectangular area in the frame buffer */
rect.top   = y;        rect.bottom = y + ry - 1;
```

**`rect` 的四个值全是像素坐标，且 `right`/`bottom` 是闭区间（含端点）**。`mx = msx * 8` 明写 `/* MCU size (pixel) */`。

**4:2:0 下 MCU = 16×16 像素** → 每次回调一块 16×16 像素区域。240 宽 = 15 块。

**⚠️ 边缘 MCU 会被裁剪**：`rx`/`ry` 在图像右/下边界处小于 16 —— **不能假设每块都是 16×16**。240 是 16 的整数倍（15×16），但 320 也是（20×16），所以我们的图刚好不裁剪；**换任何非 16 倍数的图都要按 `rect` 实际值 memcpy，不能硬拷 256 像素。**

#### 输出回调的处理

```c
// 伪代码
static int tjpgd_output_cb(JDEC *jdec, void *bitmap, JRECT *rect) {
    // bitmap 指向 rect 区域（RGB565，小端 uint16）
    // rect 全是像素坐标，right/bottom 是闭区间
    // 把这块 MCU 拼进当前 line buffer 的对应位置
    // 当 rect->bottom 满了 16 行 → 切换缓冲并 draw_bitmap
    return 1;   // 1 = 继续解码；0 = 停止（JDR_INTR）
}
```

⚠️ **`bitmap` 指向 `jd->workbuf`** —— TJpgDec 复用同一个缓冲。**必须在回调返回前把数据拷走**，不能留指针。

### RGB565 字节序：红蓝互换就出在这里

🟢 **一手核 `tjpgd.c`（RT-Thread fork）的 RGB565 转换原文**：

```c
if (JD_FORMAT == 1) {
    uint8_t *s = (uint8_t*)jd->workbuf;
    uint16_t w, *d = (uint16_t*)s;
    do {
        w  = (*s++ & 0xF8) << 8;   /* RRRRR----------- */
        w |= (*s++ & 0xFC) << 3;   /* -----GGGGGG----- */
        w |=  *s++ >> 3;           /* -----------BBBBB */
```

输出是**主机字节序的 uint16**（ESP32 小端）→ 内存里**低字节（BBBB 侧）在前**。

而 ST7789 默认按**大端（MSB first）** 收色。直接把 TJpgDec 的输出交给 `draw_bitmap`，**会红蓝互换**。

#### ✅ 正确解法：用 `.data_endian` 切面板字节序（**推荐路线 A：LITTLE**）

🟢 **ST7789 驱动源码自己处理这件事**（`esp_lcd_panel_st7789.c`，v5.5 与 v6.1 逻辑一致）：

```c
st7789->ramctl_val_2 = 0xf0;    // Use big endian by default
if ((panel_dev_config->data_endian) == LCD_RGB_DATA_ENDIAN_LITTLE) {
    // Use little endian
    st7789->ramctl_val_2 |= ST7789_DATA_LITTLE_ENDIAN_BIT;
}
```

**这是 ST7789 的 `RAMCTL` 寄存器位 —— 面板自己会按你选的字节序解释像素。**

| 配置 | 结果 |
|---|---|
| `.data_endian = LCD_RGB_DATA_ENDIAN_BIG`（**默认，MSB first**） | 面板按大端解释 → **必须给 TJpgDec 的大端缓冲** |
| `.data_endian = LCD_RGB_DATA_ENDIAN_LITTLE` | 面板按小端解释 → TJpgDec 的原生输出直接可用 |

**两条路，选一条即可**：

**路线 A（推荐，最省事）**：`.data_endian = LCD_RGB_DATA_ENDIAN_LITTLE` → 面板切到 LSB-first，TJpgDec 出来的小端缓冲**原样丢进 `draw_bitmap`，零 memcpy、零 bswap**。

**路线 B**：保持默认 BIG，在拷贝进 draw buffer 时用 `__builtin_bswap16()` 逐像素交换。

⚠️ **别两条同时做** —— 做了 A 再 bswap，红蓝互换会以另一种形式回来。

⚠️ **首屏自检必看颜色**：画纯红和纯蓝两个方块。红蓝互换 = 字节序配错，或 `.rgb_ele_order` 填成了 BGR。

### `esp_lcd_panel_dev_config_t`：v5.5 与 v6.1 结构体不同

🟢 **一手核 `components/esp_lcd/include/esp_lcd_panel_dev.h` 两版全文**。

**v5.5**：

```c
typedef struct {
    int reset_gpio_num;                       /* 不用则 -1 */
    union {
        esp_lcd_color_space_t color_space;    /* @deprecated */
        lcd_color_rgb_endian_t rgb_endian;    /* @deprecated → 用 rgb_ele_order */
        lcd_rgb_element_order_t rgb_ele_order; /* RGB 或 BGR */
    };
    lcd_rgb_data_endian_t data_endian;         /* 多字节颜色数据的字节序 */
    uint32_t bits_per_pixel;                   /* 16 */
    struct {
        uint32_t reset_active_high: 1;        /* 1 = 高电平复位 */
    } flags;
    void *vendor_config;
} esp_lcd_panel_dev_config_t;
```

**v6.1（结构体瘦身，字段顺序也变了）**：

```c
typedef struct {
    lcd_rgb_element_order_t rgb_ele_order;
    lcd_rgb_data_endian_t data_endian;
    uint32_t bits_per_pixel;
    gpio_num_t reset_gpio_num;                /* int → gpio_num_t */
    void *vendor_config;
    struct {
        uint32_t reset_active_high: 1;
    } flags;
} esp_lcd_panel_dev_config_t;
```

**v5.5 → v6.1 的真实 breaking change（Gemini 说错了方向）**：

| 变化 | 影响 |
|---|---|
| **删掉 `union`**（`color_space` / `rgb_endian` / `rgb_ele_order` 三合一） | 写 `.rgb_endian = ...` 在 v6.1 **直接编译失败** |
| **`lcd_color_rgb_endian_t` 类型和 `LCD_RGB_ENDIAN_RGB/BGR` 宏被删** | v5.5 能用的老写法 v6.1 没有 |
| `reset_gpio_num` 类型 `int` → `gpio_num_t` | 一般兼容，但 `-1` 语义要留意 |
| `lcd_color_conv_config_t` → `lcd_color_conv_yuv_config_t` | 与我们无关（不做 YUV） |

**结论：v5.5.x 的 `.rgb_ele_order` 写法不能直接搬到 v6.1。** 这正是选 v5.5.x 更省事的理由 —— 但更重要的理由是**结构体本身会变**，不是驱动被剥离。

**我们要用的字段（两版都有）**：

- `.rgb_ele_order = LCD_RGB_ELEMENT_ORDER_RGB`（不是 BGR！ST7789 的 `MADCTL` BGR 位由这个决定）
- `.data_endian` —— 见上一节
- `.bits_per_pixel = 16`
- `.reset_gpio_num = 8`（ST7789 RESET 通常低有效 → `.flags.reset_active_high = 0`，默认就是 0）
- **不存在** `.rgb_bit_order` 这类字段，别照抄别处。

### 内部 SRAM 预算

| 用途 | 大小 |
|---|---|
| TJpgDec 工作内存（`JDEC` + 流缓冲） | ~3.1KB |
| line buffer × 2（双缓冲方案） | 15.4KB |
| WebSocket 收帧 buffer | 放 PSRAM，不占内部 |
| **合计内部 SRAM** | **~18.5KB** |

S3 内部 SRAM 512KB，扣掉 Wi-Fi 栈仍充裕。

**PSRAM 只用于存 JPEG 字节，不做 DMA 源** —— draw buffer 必须在内部 SRAM。

## SPI 频率：起步 26MHz

🟡 **v1 先设 26MHz，稳定后再试 40MHz。**

| 频率 | 整屏传输时间（240×320×2 = 153600 字节） |
|---|---|
| 40MHz | 30.7ms |
| 26MHz | 47.2ms（240/9 = 26.67MHz） |
| 20MHz | 61.4ms |

**为什么降到 26MHz**：杜邦线 20–30cm 走 40MHz 方波，高次谐波容易造成振铃与采样错位 → 花屏。花屏比慢更恼火。

**时钟分频要整数**：240MHz / 9 = 26.67MHz、240 / 6 = 40MHz。**避开非整数分频点**，否则时钟树可能被抖动拉低。

**够用吗**：够。idle 循环 12fps（周期 83ms）+ 状态跳变帧（一次性播完）—— 26MHz 下 47ms 传一整屏，留有余量。

**v1 不引入局部刷新（脏矩形）**：全帧推写复杂度最低；我们的状态是离散跳变，局部刷新收益有限。

## WebSocket 收帧（esp_websocket_client）

> 🟢 `esp_websocket_event_data_t` 的 `payload_len` / `payload_offset` / `data_len` 字段一手核过。

> 🟡 **组件来源**：`esp_websocket_client` **不在 ESP-IDF v5.5 核心树**（`components/` 目录检索无此组件），它在 `esp-iot-solution`。用 `idf_component.yml` 引 `espressif/esp_websocket_client` 或直接 vendor 源码。2026-11-03 那次核查里，esp-iot-solution 的 raw 路径全部 404（组件管理器 registry 才是准），**默认 `buffer_size` 仍未核到**。

### 帧到达模型

**一条 WS message 可能被拆成多个 `WEBSOCKET_EVENT_DATA` 事件**。拼帧靠三字段：

| 字段 | 含义 |
|---|---|
| `payload_len` | 整个 message 的总长度 |
| `payload_offset` | 本次事件数据在 message 里的起始偏移 |
| `data_len` | 本次事件的数据长度 |

**收完的判据**：`payload_offset + data_len >= payload_len`。

### 配置

```c
esp_websocket_client_config_t ws_cfg = {
    .uri = "ws://petd.local:18860/ws",
    .buffer_size = 4096,        // 网络环形缓冲；🔴 默认值待核（Gemini 称 1024，未核到源码）
    .reconnect_timeout_ms = 3000,
    .network_timeout_ms = 5000,
};
```

🔴 `buffer_size` 默认值**没核到源码**。但无论多少，23KB 的帧必然分片，都得靠 `payload_offset` 拼帧 —— 调大只是减少分片次数。

### 收帧 buffer 放 PSRAM

```c
s_rx_buf = heap_caps_malloc(32 * 1024, MALLOC_CAP_SPIRAM);
```

**收帧 buffer 放 PSRAM**（内部 SRAM 要留给解码）。每收一块：

```c
memcpy(s_rx_buf + data->payload_offset, data->data_ptr, data->data_len);
if (data->payload_offset + data->data_len >= data->payload_len) {
    // 一帧收完：校验 PETF 头 → 取 payload → 送解码队列
}
```

⚠️ **不要在 WS 回调里直接解码** —— 回调跑在 event loop 线程，TJpgDec 解一帧要 20–30ms，会阻塞事件循环。回调只负责 memcpy 拼帧，收满后丢进队列，由独立任务解码。

### 重连

`esp_websocket_client` 自带重连。`WEBSOCKET_EVENT_CONNECTED` 后设备重发 `hello`，petd 补推当前状态帧 —— 时序闭环。

## 固件升级（不做 OTA）

🔴 **本项目不做 OTA 升级。** 固件只能手动 USB 烧录，设备运行时不会自己拉固件。

理由：OTA 要设备自己下载、校验 sha256、切启动分区 —— 这条链路要写下载器、
要处理断点、要处理校验失败后的回滚，出错就是变砖。而升级频率极低
（协议不变就不用刷固件），手动烧录一次几分钟。

**不做网页在线刷机**：ESP32-S3 DevKitC-1 两个 USB-C 的 5V 相通，
在线刷机页面会诱导用户同时插 PC 和充电头。

## Flash mode：DIO 而非 QIO

`sdkconfig.defaults` 里设的是 **DIO**，不是 QIO。

ESP32-S3 上 Octal(OPI) PSRAM 与 flash 共用 SPI0 外设组，flash 跑 QIO 时两者会互相干扰，
典型症状是**板子起不来**（bootloader 阶段就卡住，串口无输出）。DIO 对 Quad / Octal PSRAM 都安全，
所以这是保守选择。

> 🟡 **这一条是经验结论，我没有从 ESP-IDF v5.5 源码里逐行核实过。**
> 上机若起不来，先把这里改成 QIO 试；反过来若 QIO 能跑，也可以改回来提性能。
