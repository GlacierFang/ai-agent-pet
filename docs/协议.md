# 设备协议 petd ↔ ESP32-S3（v1）

> 🟢 petd 与固件都按本文实现，**协议已冻结**。要改的话两边同时改。

## 0. 范围

本文定义**设备 ↔ petd** 的线上协议。**petd ↔ gateway** 已在 `docs/状态语义.md` 定案，本文不重复。

三条边界（不可违反）：

1. 设备只连 petd，**不直连 gateway**，也不持有 gateway 凭据。
2. 设备**不理解业务语义** —— 状态名、页面含义、旋钮语义全在服务端。
3. 设备**不放中文字库**，所有文字由服务端渲染进 JPEG。

## 1. 传输层

| 项 | 值 |
|---|---|
| 协议 | WebSocket（RFC 6455） |
| 角色 | 设备是**客户端**，主动连 petd |
| 地址 | `ws://<petd-host>:18860/device` |
| 主机名 | 配网时手填的服务端地址（IP 或 IP:端口）。**不靠 mDNS** —— `petd.local` 在很多网络里解析不了 |
| 子协议 | `petd.v1`（必须请求；服务端不接受则 close 1002） |
| 单端口 | 18860 同时承载 WS `/device`、HTTP `/admin/`、HTTP `/admin/api/*`、mDNS 应答 |

**为什么设备做客户端**：petd 可能在无固定 IP 的局域网里；设备主动来连，petd 只需要认连接。

## 2. 握手与版本协商

设备连上后 **必须** 先发 `hello`。服务端 5s 内没收到就 close 1002。

设备 → petd：

```json
{
  "type": "hello",
  "protocol": 1,
  "deviceId": "esp32s3-a1b2c3",
  "fw": "0.1.0",
  "hostname": "pet-desk",
  "capabilities": {
    "display": { "w": 240, "h": 320 },
    "decoder": "tjpgdec",
    "colorFormat": "rgb565",
    "rotary": true
  }
}
```

petd → 设备：

```json
{
  "type": "welcome",
  "protocol": 1,
  "session": "3f1c...",
  "server": "petd/0.1.0",
  "render": {
    "width": 240, "height": 320,
    "jpegQuality": 85, "subsampling": 2,
    "colorFormat": "rgb565"
  },
  "pages": ["face", "session", "notify"],
  "density": { "levels": [0, 1, 2], "current": 1 },
  "gestures": { "longPressMs": 600, "stepsPerAction": 4 },
  "frame": { "idleFps": 1, "activeFps": 10, "binaryType": "jpeg" }
}
```

`protocol` 不相等 → petd 发 `{"type":"error","code":"PROTOCOL_MISMATCH"}` 然后 close 1002。
设备侧看到非 1 的 protocol，应停止重连并在屏幕上显示「版本不匹配」。

## 3. petd → 设备 消息

| type | 时机 | 载荷 |
|---|---|---|
| `welcome` | 握手应答 | 见 §2 |
| `frame` | 渲染完成 | **文本预告**，紧跟一条 binary 消息 |
| `setDensity` | 换信息密度 | `{"type":"setDensity","level":2}` |
| `refresh` | 强制重渲染 | `{"type":"refresh","id":12}` |
| `state` | 状态变化 | `{"type":"state","state":"working","since":1699,"text":"..."}` |
| `error` | 服务端错误 | `{"type":"error","code":"...","message":"..."}` |
| `games` | 启用哪些游戏 | `{"type":"games","enabled":["dice","snake"]}` |
| `pack` | 下发一个游戏包 | **文本预告**，紧跟一条 binary 消息（pack 原文） |
| `gameCommand` | 让设备干点什么 | `{"type":"gameCommand","action":"menu"}` |

## 4. 设备 → petd 消息

| type | 何时 | 载荷 |
|---|---|---|
| `hello` | 连上后立刻 | 见 §2 |
| `ack` | 执行完带 id 的指令 | `{"type":"ack","id":12}` |
| `frameAck` | 一帧渲染完成 | `{"type":"frameAck","id":41}` |
| `input` | 旋钮原始事件 | 见 §6 |
| `status` | 30s 周期 + 变化时立即 | 见下 |
| `log` | 调试日志（进 petd 诊断页） | `{"type":"log","level":"warn","msg":"..."}` |
| `error` | 设备端错误 | 同上 error 格式 |
| `packAck` | 收到游戏包 | `{"type":"packAck","id":"dice","ok":true}` |
| `gameMode` | 屏幕归属变了 | `{"type":"gameMode","mode":"playing"}` |
| `gameRequest` | 我要这个包 | `{"type":"gameRequest","id":"dice"}` |

`pack` 预告的载荷：

```json
{"type":"pack","id":"dice","version":1,"bytes":4770}
```

紧随其后的 binary 消息是 pack 的 JSON 原文，字节与仓库里的 pack 文件完全一致。
设备把它原样写进 SPIFFS —— 不在设备上重新序列化 JSON。

> 两条消息必须挨着发。设备靠预告判断「下一条 binary 是 pack 本体」，
> 中间夹进别的 binary 就会串包。

`status` 载荷：

```json
{
  "type": "status",
  "ts": 1699123456,
  "fw": "0.1.0",
  "uptime": 123456,
  "heapFree": 184320,
  "rssi": -52,
  "fps": 9.2,
  "decodeMs": 18,
  "lastFrameMs": 42,
  "frameErrors": 0
}
```

**预留字段**（固件 v0.2.0 起配网落地后才会上报，petd 已经收下并存着）：

| 字段 | 类型 | 含义 |
|---|---|---|
| `ip` | 字符串 | 设备自己的 IP —— 后台引导页用来说明「设备已经拿到地址」 |
| `provisioned` | 布尔 | 设备是否已完成配网 —— 决定后台「配网」这一步算不算做完 |

固件不上报这两个字段时，petd 保持默认值（`""` / `false`），旧固件不受影响。

## 5. 二进制帧：JPEG

**一帧 = 一条文本预告 + 紧跟的一条 binary WS 消息。**

文本预告：

```json
{ "type": "frame", "id": 41, "bytes": 9123, "mime": "image/jpeg" }
```

binary 消息 = **完整 JPEG**（`FFD8` … `FFD9`），**不带任何自定义头**。

这样做的好处：

- binary 是纯 JPEG → 后台预览、诊断页存图、OTI 调试都能直接用，不用剥头。
- 文本预告带 `id` → 设备能回 `frameAck`，petd 能做背压。
- 未来换 PNG / WebP 只改 `mime`，设备按 `mime` 分派。

约束：

- 宽高 ≤ `render.width/height`；petd 保证按此渲染。
- 单帧 ≤ 32KB；超了 petd 降 quality 重渲。
- **v1 不做增量刷新**，每次都是整帧。
- 设备需 **双缓冲**：一张在解码渲染，一张在接收新帧。PSRAM 至少同时放 2×32KB。

**背压**：petd 在飞帧数（已发未 ack）> 2 时**直接丢弃中间帧**，只保最新一张。宠物不需要补帧。

## 6. 旋钮事件（设备只报原始量）

设备**只上报原始测量值**，不做业务判断 —— 短按/长按的分派在 petd 侧按 `longPressMs` 阈值完成。

```json
{ "type": "input", "ev": "rot", "dir": 1, "steps": 3 }
{ "type": "input", "ev": "press", "btn": "sw", "ms": 120 }
{ "type": "input", "ev": "press", "btn": "sw", "ms": 900 }
{ "type": "input", "ev": "rot_press", "dir": -1, "steps": 2 }
```

| ev | 设备侧判定 | 上报 |
|---|---|---|
| `rot` | ENC 有变化，SW 未按下 | `dir` +1/-1，`steps` 为本次累加的脉冲数 |
| `press` | SW 按下并释放 | `ms` 为按住时长，**设备不判断长短** |
| `rot_press` | SW 按住期间 ENC 有变化 | `dir` + `steps`；释放后不再补 press |

**为什么长按不在设备端判定**：阈值是业务语义，改阈值不该刷固件。petd 按 `gestures.longPressMs`（默认 600ms）把 `press` 分成 `press_short` / `press_long`。

设备把 30ms 窗口内的多个脉冲聚合成一条 `rot`，`steps` 为累计值。


## 7. 信息密度（服务端语义）

屏上不再有「页面」—— 只有宠物形象和 feature 卡片，整屏互斥。
宠物那一屏是「文字带在上、宠物在下」，密度只影响文字带显示几行字（1 / 2 / 3 行）。

| 动作 | 语义 |
|---|---|
| 短按 press | 摇骰子（赛博骰子，一次性覆盖层） |
| 长按 press | 刷新会话状态 |
| 旋转 rot | 翻到下一张 feature 卡 |
| 按住+旋转 rot_press | 信息密度循环 |

信息密度分三档：0 只有宠物形象，1 加一行状态说明，2 再加会话名。

## 8. 状态映射

gateway 会话 → 宠物状态。优先级从上到下：

| 状态 | 条件 |
|---|---|
| `waiting` | `permissionModePending=true` 或 `unread=true` |
| `error` | `status=error` |
| `working` | `status=running` 且 `hasActiveRun=true` |
| `done` | `status=done` |
| `idle` | `status=running` 且 `hasActiveRun=false`；`status` 缺省也归这里 |
| `sleeping` | 持续无活动 N 分钟（可配，默认 10） |

`isBackground=true` 的后台会话**不参与**状态映射。
多会话时，**每个会话各自判状态，宠物取最急的那个**（同级取最近活动的）。归因见 `pet.attribution`，计数见 `pet.counts`。
**焦点不改状态**：旋钮选中的会话只决定会话卡片看哪条，不改变宠物状态。

## 9. 帧节奏

服务端**状态驱动**渲染，不是视频流。

| 状态 | 上限帧率 | 触发 |
|---|---|---|
| `idle` / `sleeping` / `done` | 1 fps | 状态变化立即推一帧 |
| `working` / `waiting` / `error` | 10 fps | 同上 |

任何 `setDensity` / `state` 变化 → **立即推一帧**。

## 10. 断线与重连

- petd 每 20s 发 WS ping，10s 无 pong → 关闭连接。
- 设备重连退避：1s, 2s, 4s, 8s, 16s, 30s（封顶），成功后归零。
- 重连后重新 `hello` → 重新拿 `welcome` → 立即渲一帧。
- petd 侧：设备断开即释放其会话状态；后台「连接与诊断」页的设备状态显示离线。

## 11. 固件升级

**OTA 协议从 0.5.4 起就有，能实际走通的固件是 0.5.7 起**（0.5.4 到 0.5.6 的 hello 握手有缺陷，收不到推送）。升级只由后台的人点 —— 设备不会自己判断要不要升。

| 消息 | 方向 | 载荷 |
|---|---|---|
| `otaStart` | petd → 设备 | `{"type":"otaStart","version":"0.5.8","bytes":1062352,"round":3}` |
| `otaChunk` | petd → 设备 | **文本预告**，紧跟一条 binary 本体（16KB） |
| `otaFinish` | petd → 设备 | `{"type":"otaFinish"}` |
| `otaStatus` | 设备 → petd | `{"type":"otaStatus","state":"downloading","seq":5,"percent":42,"version":"0.5.8","ok":true,"round":3}` |

**下发是「确认驱动」的，不是「一口气灌完」的。**

设备每写完一片 flash 就回一条 `otaStatus`（带 `seq`），petd 收到这一片的
确认才发下一片。**不等确认直接往下推，设备的收包队列（深 4）会被顶爆，
WebSocket 收包任务被堵死，连接直接断在半路** —— 真机表现是「下发中断在
第 16 片」，而且每次断的片数都不一样。

确认必须是 **0..N 连续**的：只看「最大 seq」不够，上一轮 OTA 迟到的确认
会把中间的空缺填上，看起来像连续，镜像就写坏了。`round` 是这一轮 OTA
的编号（petd 在 `otaStart` 里给，设备在 `otaStatus` 里回），用来把
上一轮迟到的确认挡掉。

设备写盘失败会带 `ok:false` —— petd 立刻停手，不再往设备推坏数据。

从 **0.5.9** 起，设备端还能**中途作废**没下完的一轮 OTA 自己重来
（断线就 abort 掉那个分区）。更老的固件遇到这种情况只能给设备断电重启。

- 写的是非当前运行分区（`ota_0` / `ota_1`），校验通过才切启动分区重启
- **只认 app 镜像** `petd.bin` —— `merged-binary.bin` 含 0x0 头，登记了会覆盖分区表
- 设备固件 **≥ 0.5.7** 才认这些消息（0.5.4 到 0.5.6 握手有缺陷，连不上就收不到推送）

首次上 0.5.7 仍要 USB 整片刷，步骤见 [部署手册](部署手册.md)。

**不做网页在线刷机**：在线刷机页面会诱导用户同时插 PC 和充电头，而 ESP32-S3 DevKitC-1 两个 USB-C 的 5V 相通。

**不做网页在线刷机**：在线刷机页面会诱导用户同时插 PC 和充电头，而 ESP32-S3 DevKitC-1 两个 USB-C 的 5V 相通。

## 12. 错误码

| code | 含义 |
|---|---|
| `PROTOCOL_MISMATCH` | protocol 不匹配 |
| `HELLO_TIMEOUT` | 5s 内没收到 hello |
| `BAD_FRAME` | JPEG 损坏 / 尺寸不符 |
| `DECODE_FAIL` | TJpgDec 解码失败 |
| `SPI_TIMEOUT` | SPI 事务超时 |
| `LOW_HEAP` | 内部 SRAM 不足 |

## 13. 安全边界

- 设备**不持有 gateway 凭据**，只连 petd。
- petd 的 gateway 凭据走本地配置（最小权限 `operator.read`）。
- 局域网内 WS 与 `/admin/` **均不鉴权** → petd **只允许绑定内网地址**。
- 设备不解释业务语义、不存中文字库、不存 gateway 凭据。
- 设备不做「自己判断要不要升级」—— OTA 只在后台被人点之后才发生。

## 附录 A：gestures.json

`petd/data/gestures.json`（旋钮语义配置，服务端读）：

```json
{
  "version": 4,
  "longPressMs": 600,
  "stepsPerAction": 4,
  "actions": {
    "rot":        "card.next",
    "rot_press":  "density.cycle",
    "press_long": "state.refresh",
    "press_short": "game.menu"
  }
}
```

**没有 pages，也没有 bindings** —— 屏上没有多页面（宠物形象和内容卡整屏互斥），
所以手势表不分模式，一张表管所有屏。

`longPressMs` 是**长按阈值**，服务端按它把 `press` 分成短/长；`stepsPerAction` 是
**旋转几步触发一次动作**。两者都在服务端，改配置不刷固件。

旋钮编码器一个齿 = 一步（实机确认）：转一个齿翻一张卡。固件按编码器边沿累加步数上报 `rot` 事件。
`stepsPerAction` 由服务端配置（`petd/data/gestures.json`）并随 `welcome` 下发，固件不使用该字段。
